# Status

The pilot, the harness, durable state and our records in the database are built, from `docs/PLAN.md`, `docs/PLAN_HARNESS.md`, `docs/PLAN_DURABLE.md` and `docs/PLAN_RECORDS.md`. Run it with `npm run dev` (backend on :8000, the agent's service on :8002, dashboard on :5173) and check it with `npm run check`, which needs no `.env`. `.env` holds `OPENROUTER_API_KEY`, `DATABASE_URL` (the Supabase session pooler) and the Langfuse keys. The first time on a Supabase project, and whenever you want the queue back as it was, stop `npm run dev` and run `npm run seed`. The agent needs `DATABASE_URL`; the backend and the tests fall back to SQLite (`backend/undercover.db`, gitignored) without it. Start runs with `uv run -m agent [--cap N | --claim CLM-1001]`.

- `backend/`: `GET /api/health`. All our records live in the database through SQLAlchemy Core: the claims with their content and state, policies, customers, plans, add-ons, handlers, company settings, and the policy wording and claims manual as `##`-headed sections, plus steps and a run's to-do list (`backend/tables.py` defines the tables, `backend/reference.py` reads the records, `backend/db.py` has one engine per URL, made once and seeded when empty from `data/*.json` and `data/*.md` by `backend/seed_data.py`, the only module that opens `data/`; Supabase Postgres in the `undercover` schema with at most 4 connections when `DATABASE_URL` is set, SQLite otherwise; `backend/seed.py` resets it). The routes in `backend/main.py` are thin calls into `backend/claims.py`, `backend/runs.py` and `backend/payouts.py`, which raise `NotFound`/`Conflict` (`backend/errors.py`), turned into 404 and 409 in one place. Money is `Decimal` dollars, sent as two-decimal strings and stored as whole cents (`backend/money.py`). Operations: `list_claims`, `get_claim`, `list_sections`/`get_section`, `get_claim_instructions`/`get_queue_instructions` (`backend/instructions.py`), `list_handlers`, `calculate_payout` (the payout rules in `backend/payouts.py`, which also knows when a payout needs sign-off), `decide_claim` (once only: approve/decline/refer; an approval over the limit becomes `waiting for sign-off`; the same decision again returns the claim, a different one is 409), `record_step`, `list_claim_steps`, `sign_off_claim` (records who and when, sets `in progress`, then tells the agent's service in the background; it stands if the agent can't be reached), `pay_claim` (blocked until any sign-off, only for the approved payout, sets `decided`; a repeat returns the claim), `acquire_lease`/`release_lease` (one agent at a time works a claim: a 30-second lease the agent renews; `lease_owner` and `lease_expires_on` on the claim), `list_unfinished_claims` (stopped claims, and approved ones ready to pay, without those with a live lease), `run_agent` (one claim from the dashboard, as its own process with `python -m agent --claim`), `requeue_claim` (a failed claim starts afresh: status `waiting`, `thread` + 1), and `start_run`/`get_current_run` (null before the first run)/`update_run_item`/`finish_run` (a run's to-do list).
- `agent/`: the claim agent is a LangGraph graph (`claim_graph.py` wires it, `claim_nodes.py` has the nodes, `claim_state.py` the state): `agent` and `tools` loop (the tools are `get_claim`, `list_sections`, `read_section`, `calculate_payout`, `decide_claim`, each recording a step), then `settle` reads the decision back from the backend, `approval` waits with `interrupt()` for a sign-off, and `pay` pays. A backend refusal reaches the model as a tool message, and a claim fails after 30 model calls. Progress is saved after every step in Supabase (`checkpoint.py`, the only module that talks to Postgres, at most 2 connections, made once even when claims race for it). A claim's thread is `CLM-1001-1`; a failure moves it to the next number. The queue agent is a LangChain `create_agent` (`harness.py`). `agents.py`: `decide_claim` (start or carry on, in a context of its own so its trace is separate), `carry_on` and `run_queue`, which first carries on with stopped and signed-off claims and finishes an unfinished run. `work.py` is the retry policy in plain code (a stopped claim carries on without a new attempt; a failed claim is tried once more on a new thread, then left for a handler; a referral is left for a handler too, and each item's note is one line built from the recorded decision). `__main__.py` starts runs, `service.py` is the agent's web service (`POST /api/claims/{claim_id}/resume`, answered at once, worked in the background). `lease.py` holds the claim's lease while `decide_claim` works it and renews it every 10 seconds in a background thread; a claim another agent holds is left to that agent (its run item is `done`, noted "Being worked by another agent"), and a crashed agent's claim can be carried on after 30 seconds. The claims table has two new columns, so run `npm run seed` once after pulling this. `tracing.py` sends each claim's work to Langfuse as a trace of its own, in the session `CLM-1001-1`, so the traces from before and after a sign-off sit together. `api.py` is the only module that makes HTTP calls. The default model is `deepseek/deepseek-v4.1-flash` at low reasoning effort, or `MODEL_NAME` if set.
- `dashboard/`: amounts are whole cents inside it, converted in `api.ts` and formatted by `money.ts`. React Router, with `/` the claims queue (totals for each status and for claims left for a handler at the top), `/claims/:claimId` a claim's full page (story, items, policy, customer history, a "Run agent" button when waiting, a live step log while it works, the decision, sign-off buttons while it waits for one, then "Signed off by ... on ..." and "Payment in progress" until the agent pays, and the payment), and `/instructions`. Brand fonts and colors from `docs/BRAND.md` apply globally.
- `e2e/`: the queue lists the claims and shows a claim's status through all four states, and the current run's to-do list in all four item statuses; a decided claim's page shows its decision, payout and reason; the instructions page; a sign-off reaches the agent's service once (a stand-in on port 8003, `e2e/agentStandIn.mjs`) and the claim then shows as paid with who signed off and when. `playwright.config.ts` gives each run a fresh SQLite file in the system temp folder, so a run never touches `backend/undercover.db` and the backend never holds a file that is deleted under it, and the tests run the backend without `DATABASE_URL`.

Checked live on Supabase with the default model: a 5-claim capped run worked five claims; two over the limit waited; signing one off on the dashboard (Playwright MCP) showed it paid within five seconds with the handler and time; a run killed after its first steps carried on in the same run with the same threads, attempts unchanged and one decision each; a sign-off made while the agent's service was down was paid by the next run; Langfuse shows a held claim's session with traces from before and after the sign-off.

Known: Supabase's session pooler keeps released connections open. After reseeding, a 5-claim run with the backend and the agent's service up showed 9 connections for user `postgres` in `pg_stat_activity` (Supavisor 8, Supabase's own `pg_net` 1), the same during and after the run, and still the same 5 seconds after every one of our processes had stopped. Our processes hold at most 8 (the backend 4, the agent's service 2, a run 2), so the count is within the brief's 12. The 11 to 16 seen earlier was probably the pooler holding more connections after several runs and restarts; it was not seen again. Rejecting a held payout, sign-in, real payments and messages to customers are not built, per `docs/SPEC.md`.
