# Status

The pilot and the harness are built, from `docs/PLAN.md` and `docs/PLAN_HARNESS.md`. Run it with `npm run dev` (backend on :8000, dashboard on :5173) and check it with `npm run check`.

- `backend/`: `GET /api/health`. Reference data (plans, policies, customers, handlers, company settings, the policy wording, the claims manual) loads read-only from `data/*.json` and `data/*.md` into memory at import (`backend/data.py`); the policy wording and the claims manual are also split into their `##`-headed sections there. Claim status lives in SQLite (`backend/undercover.db`, gitignored), seeded from `data/claims.json` on first use (`backend/db.py`), alongside a run's to-do list (`runs` and `run_items`, managed in `backend/runs.py`). Operations: `list_claims`, `get_claim`, `list_sections`/`get_section` (a document's section headings, and one section's text), `get_claim_instructions`/`get_queue_instructions` (serve `backend/instructions.py`, read by both agents and the dashboard), `list_handlers`, `decide_claim` (approve/decline/refer; moves an over-limit approval to `waiting for sign-off`, else `decided`; clears any earlier sign-off and payment), `record_step` (moves a claim from `waiting` to `in progress`), `list_claim_steps`, `sign_off_claim`, `pay_claim` (blocked until any required sign-off), `run_agent` (one claim, from the dashboard; schedules the agent's run on a `BackgroundTasks` task), `requeue_claim` (puts a stuck `in progress` claim back to `waiting`), `start_run`/`get_current_run`/`update_run_item`/`finish_run` (a run's to-do list; `finish_run` is blocked, 409, while any item is still `to do` or `in progress`).
- `agent/`: two agents, both reaching the backend's API only. `main.py`'s `run(claim_id, thread_id)` decides one claim from a clean start, with tools `get_claim`, `list_sections`, `read_section`, `decide_claim` — each read and the decision also record a step, so the backend's step log reflects exactly what the agent did, including which document sections it read. `queue.py`'s `run_queue(cap=None)` is the orchestrator: it takes the first `cap` waiting claims (or all of them), starts a run, and works through the to-do list with tools `get_to_do`, `work_claim` (a fresh `run()` subagent per claim, retried once on failure, left for a handler after a second; never retries a claim that's already decided), and `finish_run` (blocked by the backend until every item is settled). `cli.py` starts either from the command line: `uv run python -m agent.cli [--cap N | --claim CLM-1001]`. The default model is `deepseek/deepseek-v4.1-flash` at low reasoning effort, or `MODEL_NAME` if set. Checked against the real model with a 5-claim capped run: see `docs/PLAN_HARNESS.md` phase 6.
- `dashboard/`: React Router, with `/` the claims queue (the current run's to-do list, when there is one, above a table of all claims with status badges), `/claims/:claimId` a claim's full page (story, items, policy, customer history, a "Run agent" button when waiting, a live step-by-step log while it works, the decision once there is one, and — once it needs one — sign-off and "Release payment" controls), and `/instructions` both agents' instructions, read only, under their own headings. Brand fonts and colors from `docs/BRAND.md` apply globally, checked in light and dark mode.
- `e2e/`: the queue lists the claims and shows a claim's status badge through all four states, and shows the current run's to-do list in all four item statuses; a decided claim's page shows its decision, payout and reason; the instructions page shows the agent's instructions; an over-limit approval blocks "Release payment" until a handler signs off. `e2e/globalSetup.ts` deletes the SQLite file before each run so every run starts from the same seeded queue.

`npm run check` passes in full: ruff, pyright, pytest (95% coverage), Prettier, ESLint, tsc, vitest (94% coverage), and the Playwright suite above.

Not built, per `docs/SPEC.md`'s "Not for now": sign-in, real payments, and messages to customers.
