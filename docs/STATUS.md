# Status

The pilot and the harness are built, from `docs/PLAN.md` and `docs/PLAN_HARNESS.md`. Run it with `npm run dev` (backend on :8000, dashboard on :5173) and check it with `npm run check`.

- `backend/`: `GET /api/health`. Reference data (plans, policies, customers, handlers, company settings, the policy wording, the claims manual) loads read-only from `data/*.json` and `data/*.md` into memory at import (`backend/data.py`); the policy wording and the claims manual are also split into their `##`-headed sections there. Claim status lives in SQLite (`backend/undercover.db`, gitignored), seeded from `data/claims.json` on first use (`backend/db.py`), alongside a run's to-do list (`runs` and `run_items`, managed in `backend/runs.py`). The routes in `backend/main.py` are thin calls into `backend/claims.py` and `backend/runs.py`, which use `db.connection()` and raise `NotFound`/`Conflict` (`backend/errors.py`), turned into 404 and 409 in one place. Money is `Decimal` dollars, sent as two-decimal strings and stored as whole cents (`backend/money.py`). Operations: `list_claims`, `get_claim`, `list_sections`/`get_section` (a document's section headings, and one section's text), `get_claim_instructions`/`get_queue_instructions` (serve `backend/instructions.py`, read by both agents and the dashboard), `list_handlers`, `decide_claim` (approve/decline/refer, once only; moves an over-limit approval to `waiting for sign-off`, else `decided`; a second decision is 409), `record_step` (moves a claim from `waiting` to `in progress`), `list_claim_steps`, `sign_off_claim`, `pay_claim` (blocked until any required sign-off; once only, and only for the approved payout, else 409), `run_agent` (one claim, from the dashboard; starts the agent as its own process with `python -m agent.cli --claim`, so the backend never imports the agent), `requeue_claim` (puts a stuck `in progress` claim back to `waiting`), `start_run`/`get_current_run`/`update_run_item`/`finish_run` (a run's to-do list; `finish_run` is blocked, 409, while any item is still `to do` or `in progress`).
- `agent/`: two agents, both reaching the backend's API only, through `api.py`, the one module that makes HTTP calls. `harness.py` is the model (with a request timeout) and `run_agent`, which knows nothing about claims. `tools.py` has every tool: the claim agent's `get_claim`, `list_sections`, `read_section`, `decide_claim` (each read and the decision also record a step, so the backend's step log reflects what the agent did, including which sections it read) and the orchestrator's `get_to_do`, `work_claim` and `finish_run`. They take the claim or the run from `ToolRuntime[ClaimContext]` / `ToolRuntime[RunContext]`. `agents.py` wires them: `decide_claim(claim_id)` decides one claim from a clean start; `run_queue(cap=None)` takes the first `cap` waiting claims (or all), starts a run, and lets the orchestrator work the to-do list. `work.py` is the retry policy in plain code: one fresh `decide_claim` subagent per claim, retried once on failure, left for a handler after a second, never retried once decided; `finish_run` is blocked by the backend until every item is settled. `cli.py` starts either from the command line: `uv run python -m agent.cli [--cap N | --claim CLM-1001]`. Both agents' instructions (`backend/instructions.py`) state a goal and the resources, not steps. The default model is `deepseek/deepseek-v4.1-flash` at low reasoning effort, or `MODEL_NAME` if set. After the code review (`docs/HUMAN_REVIEW_HARNESS.md`) it was checked against the real model: a 5-claim capped run on `openrouter/free` (3 decided; 2 left for a handler by the free tier's 20-requests-a-minute limit, then put right by running them on the default model).
- `dashboard/`: amounts are whole cents inside it, converted from and to the API's strings in `api.ts` and formatted by `money.ts`. React Router, with `/` the claims queue (the current run's to-do list, when there is one, above a table of all claims with status badges), `/claims/:claimId` a claim's full page (story, items, policy, customer history, a "Run agent" button when waiting, a live step-by-step log while it works, the decision once there is one, and — once it needs one — sign-off and "Release payment" controls), and `/instructions` both agents' instructions, read only, under their own headings. Brand fonts and colors from `docs/BRAND.md` apply globally, checked in light and dark mode.
- `e2e/`: the queue lists the claims and shows a claim's status badge through all four states, and shows the current run's to-do list in all four item statuses; a decided claim's page shows its decision, payout and reason; the instructions page shows the agent's instructions; an over-limit approval blocks "Release payment" until a handler signs off. `e2e/globalSetup.ts` deletes the SQLite file before each run so every run starts from the same seeded queue.

`npm run check` passes in full: ruff, pyright, pytest (99% coverage, including `agent/tests/test_structure.py`, which keeps HTTP in `api.py`, tools at module level and SQL out of routes), Prettier, ESLint (which keeps `fetch` in `dashboard/src/api.ts`), tsc, vitest (93% coverage), and the Playwright suite above.

Not built, per `docs/SPEC.md`'s "Not for now": sign-in, real payments, and messages to customers.
